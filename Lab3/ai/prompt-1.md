# Промт 1

Проаналізуй файл spec.md та підготуйся до генерації файлу diagrams.md із трьома детальними Sequence-діаграмами у Mermaid для сценаріїв прецеденту UC_Return.

# Аналіз та пропозиції AI
1. Використати єдиний порядок учасників у всіх трьох діаграмах: Reader, ReturnController, LoanService, LoanRepository, BookRepository, ReaderRepository, PaymentGateway, EmailService.
2. У Сценарії 1 додати alt для перевірки валідності та терміну позики, а також opt для перевірки наявності Reader.email перед відправкою листа.
3. У Сценарії 2 повертати підтвердження оплати від PaymentGateway через ReturnController, додати loop для повторної спроби/очікування статусу оплати та alt на результат транзакції (підтверджено / відхилено).
4. У Сценарії 3 використати окремий метод reportLostBook(loanId), одразу змінити статус книги на LOST, нарахувати 500.00 грн без пені та додати alt на результат оплати.

# Моє рішення та відповідь
1. Щодо учасників: єдиний порядок усіх 8 учасників у трьох діаграмах підходить.
2. Щодо Сценарію 1: alt на перевірку терміну позики та opt на наявність email залишаємо, все логічно.
3. Щодо Сценарію 2: прибери проміжний колбек від PaymentGateway через ReturnController - нехай LoanService напряму викликає processPayment(loanId, amount) у PaymentGateway і напряму отримує відповідь назад, щоб не розривати activation bars. У loop для оплати вкажи умову повтору (до 3 спроб при таймауті).
4. Щодо Сценарію 3: варіант із reportLostBook(loanId) та негайним переведенням книги в статус LOST затверджую.
