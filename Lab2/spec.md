# Специфікація вимог та Use Cases (Library-system)

## Намір
Описати функціональні та нефункціональні вимоги до системи управління бібліотекою, змоделювати прецеденти (Use Cases) та детальні сценарії поведінки для процесу повернення книги.

## Предметна область (узгоджено з ER-моделлю Лаб 1)
- Актори:
  - Reader (Читач) - людина.
  - PaymentGateway (Платіжний шлюз) - зовнішня система.
  - EmailService (Сервіс розсилок) - зовнішня система.
- Сутності та атрибути:
  - Reader (id: uuid, email: string, full_name: string)
  - Author (id: uuid, full_name: string)
  - Book (id: uuid, title: string, publication_year: number, status: enum [AVAILABLE, LOANED, LOST])
  - Loan (id: uuid, reader_id: uuid, book_id: uuid, borrow_date: date, return_date: date, fine_amount: decimal)

## Критерії прийняття для AI
1. Use Case діаграма у синтаксисі Mermaid (для вставки в Markdown):
   - Мінімум 2 типи акторів (людина та зовнішні сервіси).
   - Використати зв'язки include, extend та узагальнення (generalization).
2. Функціональні вимоги (FR) у класичному англійському синтаксисі EARS (WHEN / IF / WHILE ... THEN the System SHALL ...).
3. Нефункціональні вимоги (NFR) окремим блоком після FR:
   - Однозначні метрики з числами та межами (час відгуку, навантаження, безпека, пристрої/мова).
   - Не наносяться на Use Case діаграму та не входять до матриці трасування.
4. Сценарії Gherkin (Given/When/Then) для одного складного Use Case (UC_Return - Повернення книги):
   - User story інтегрується безпосередньо в опис фічі/сценарію (окремий розділ User Stories не потрібен).
   - Мінімум 3 сценарії: вчасне повернення, повернення з простроченням та оплатою штрафу, повернення втраченої книги.
   - Зовнішні системи (PaymentGateway, EmailService) виступають активними акторами дій.
5. Матриця трасування (Markdown таблиця):
   - Зв'язки багато-до-багатьох (N:M) між FR (EARS), Use Cases та Gherkin-сценаріями.
   - Мінімум 1 непокрита функціональна вимога з поясненням.
